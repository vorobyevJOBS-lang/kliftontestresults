## Что сделано в этой ветке

- `p3_result_preservation_and_backup.sql` (идемпотентная, ничего не меняет в строках,
  финальная сверка количества и отпечатков 16 таблиц перед `commit`):
  - триггер «только добавление» для `candidate_profiles`, `candidate_activity`;
  - запрет DELETE/TRUNCATE для `organizations`, `assessment_invites`,
    `assessment_evidence`, `assessment_reference_checks`, `outcome_followups`,
    `candidate_notes`, `audit_events`;
  - неизменяемость отправленного ответа кандидата (разрешено только проставить
    `opened_at`);
  - запрет `DROP TABLE` для защищённых таблиц (если event trigger недоступен,
    миграция продолжится с сообщением);
  - `get_data_integrity_report()` и `export_owner_backup()` — только для владельца;
    хэш токена приглашения не выгружается; каждая выгрузка пишется в `audit_events`.
- `scripts/create-encrypted-full-backup.mjs` — полная зашифрованная копия
  (AES-256-GCM), файл и ключ с датой в имени, не перезаписывает существующие,
  копия пишется даже при несовпадении манифеста (код выхода 2).
- Кабинет кандидата хранит неподтверждённые ответы в `localStorage` (ключ — хэш
  токена, срок 14 дней, удаляется после сохранения и после отправки). Локальная
  копия восстанавливается, только если серверный черновик не менялся с другого
  устройства.

Миграция проверена на локальном PostgreSQL 16 с упрощённой схемой: повторное
применение проходит; UPDATE отправленного ответа, DELETE приглашений, DELETE
организации (каскад), `DROP TABLE` защищённых таблиц — отклоняются; черновики,
отправка и `opened_at` работают; не-владелец и аноним получают отказ в RPC.

## Что нужно сделать владельцу

1. Применить `p3_result_preservation_and_backup.sql` в Supabase SQL Editor
   (после P0–P2). Если появится сообщение «table-drop guard skipped», остальная
   защита всё равно установлена.
2. Сразу сделать полную копию:
   `EVIDENCEHIRE_OWNER_EMAIL=... EVIDENCEHIRE_OWNER_PASSWORD=... node scripts/create-encrypted-full-backup.mjs`
   и проверить её `node scripts/verify-encrypted-legacy-backup.mjs <файл> <ключ>`.
3. Разнести файл копии и ключ по двум разным местам вне этого Mac (например,
   зашифрованное облако и менеджер паролей). Повторять еженедельно и перед
   каждой миграцией.
4. Рассмотреть Supabase Pro (ежедневные бэкапы / PITR) — это единственная
   защита от потери данных на стороне провайдера.
5. Раз в квартал восстанавливать копию в отдельный тестовый проект Supabase.
6. Позже: перенести старые `*_schema.sql`, `branch_access_migration.sql`,
   `fix_prim_results_visibility.sql` в папку `legacy_sql/` с пометкой «не запускать»
   и удалить неподключённый старый код админки.
